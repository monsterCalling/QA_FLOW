# QA Strategy

## 1. Назначение

Этот документ задаёт базовую стратегию тестирования приложения и используется QA-агентами как постоянный контекст.

Цель QA — не только обнаружение дефектов после реализации, а обеспечение качества на всём жизненном цикле change:

1. анализ спецификации до разработки;
2. оценка рисков;
3. анализ влияния change на существующее покрытие;
4. проектирование ручных и автоматизированных проверок;
5. проверка соответствия реализации спецификации;
6. выполнение тестов;
7. анализ результатов;
8. подтверждение достаточности покрытия;
9. формирование QA verdict.

## 2. Базовые принципы

### 2.1. Shift Left

QA подключается до начала разработки.

Любой change должен быть проверен на:

- однозначность;
- полноту;
- тестируемость;
- непротиворечивость;
- наличие ожидаемого поведения;
- наличие негативных и пограничных сценариев;
- влияние на существующую функциональность;
- влияние на данные и интеграции.

### 2.2. Risk-Based Testing

Глубина тестирования определяется не количеством требований, а риском.

Приоритет получают сценарии, затрагивающие:

- критичные бизнес-процессы;
- финансовые операции;
- состояние и целостность данных;
- интеграции;
- Kafka;
- внешние системы;
- авторизацию и права;
- идемпотентность;
- повторную обработку;
- конкурентность;
- обратную совместимость.

### 2.3. Traceability

Для каждого значимого требования должна быть прослеживаемость:

`Requirement → Risk → Test Condition → Manual Test / Autotest → Execution Result`

Если связь отсутствует, покрытие считается неполным.

### 2.4. Manual + Automation

Ручные тесты и автотесты не являются взаимоисключающими.

Один критичный сценарий может одновременно:

- иметь подробный ручной test case;
- быть частью regression checklist;
- быть покрыт автотестом.

Автоматизация определяется ценностью и повторяемостью сценария, а не желанием добиться формального процента automation coverage.

### 2.5. Evidence-Based QA

Вывод QA должен основываться на наблюдаемом результате.

Если применимо, проверяются:

- API response;
- бизнес-результат;
- состояние БД;
- Kafka events;
- side effects;
- интеграционные вызовы;
- логи;
- итоговое состояние сущности.

HTTP 200 сам по себе не доказывает успешность бизнес-сценария.

## 3. Обязательные QA-артефакты

Для change могут создаваться:

- spec review;
- risk analysis;
- test model impact report;
- test design;
- manual tests;
- automation plan;
- autotests;
- spec-vs-code report;
- test execution results;
- failure analysis;
- coverage report;
- QA verdict.

## 4. Human-in-the-Loop

LLM не принимает окончательное решение там, где требуется бизнес-контекст или высока цена ошибки.

Для `spec-review` и `risk-analysis` используется priority-aware gate согласно `priority-policy.md`:

- `spec-review` задаёт material clarification questions интерактивно во время анализа;
- `CRITICAL` finding → hard stop;
- `HIGH/MEDIUM` finding → Human Review;
- только `LOW/TRIVIAL` findings ниже thresholds или findings нет → lightweight Confirmation Gate;
- `spec-review` никогда не переходит дальше без explicit human confirmation;
- `CRITICAL/HIGH/MEDIUM` risks → Human Review, но сам risk не означает requirement defect;
- только `LOW/TRIVIAL` risks → продолжить автоматически.

Human Gate остаётся обязательным для:

- test model impact;
- test design;
- изменений manual tests;
- изменений test model;
- implementation impact;
- automation plan;
- autotest review;
- spec-vs-code mismatches;
- failure classification;
- coverage gaps;
- финального QA verdict.

## 5. Запрет на додумывание

QA-агент обязан разделять:

- `FACT` — подтверждено источником;
- `INFERENCE` — логический вывод из подтверждённых фактов;
- `ASSUMPTION` — предположение;
- `UNKNOWN` — данных недостаточно.

`ASSUMPTION` нельзя использовать как обязательное ожидаемое поведение без подтверждения человека.

Если результат зависит от неизвестного факта, агент обязан запросить clarification.

## 6. Definition of Done для QA

QA может рекомендовать `PASS`, если:

- нет открытых блокирующих замечаний по спецификации;
- CRITICAL/HIGH (legacy P0/P1) риски имеют достаточное покрытие;
- все обязательные тесты выполнены;
- нет подтверждённых критичных spec-vs-code mismatch;
- автотесты и ручные тесты дали приемлемый результат;
- отсутствуют необъяснённые падения;
- незакрытые риски явно зафиксированы;
- traceability актуальна.

Допустимые финальные статусы:

- `PASS`
- `PASS_WITH_RISKS`
- `FAILED`
- `BLOCKED`
