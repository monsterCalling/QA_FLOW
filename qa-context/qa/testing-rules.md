# Testing Rules

## 1. Общие правила

Для каждого нового или изменённого бизнес-сценария рассмотреть:

- позитивный сценарий;
- негативные сценарии;
- граничные значения;
- отсутствующие обязательные данные;
- некорректные типы и форматы;
- повторный вызов;
- повторную обработку;
- идемпотентность;
- timeout;
- retry;
- конкурентные операции;
- порядок событий;
- изменение состояния;
- права доступа;
- side effects;
- backward compatibility;
- rollback / компенсацию;
- поведение при недоступности зависимостей.

Не все пункты обязательны для каждого change. Неприменимые проверки должны быть явно отброшены с объяснением.

## 2. Проверка состояний

Если функциональность использует статусы или state machine, проверить:

- допустимые переходы;
- запрещённые переходы;
- повторный переход в тот же статус;
- переход из терминального состояния;
- переход при неполных данных;
- конкурентные переходы;
- состояние после ошибки;
- историю изменения статуса;
- consistency между API, БД и событиями.

## 3. REST API

При изменении REST API проверить:

### Contract

- HTTP method;
- endpoint;
- path parameters;
- query parameters;
- headers;
- request body;
- response body;
- типы полей;
- обязательность;
- nullable;
- enum;
- формат даты/времени;
- precision чисел.

### Validation

- отсутствующее обязательное поле;
- null;
- пустая строка;
- пробелы;
- минимальное значение;
- максимальное значение;
- меньше минимума;
- больше максимума;
- некорректный enum;
- некорректный формат;
- неожиданные поля.

### Responses

Проверить:

- HTTP status;
- business error code;
- текст/структуру ошибки;
- отсутствие stack trace во внешнем ответе;
- корректность business result.

### Security

Если применимо:

- без авторизации;
- истёкший токен;
- неверная роль;
- недостаточные права;
- доступ к чужой сущности;
- privilege escalation.

### Compatibility

При изменении существующего API проверить:

- старых consumers;
- optional/required изменения;
- удаление полей;
- изменение enum;
- изменение типов;
- семантику существующих полей.

## 4. Kafka

Для producer/consumer сценариев рассмотреть:

### Valid flow

- корректное событие;
- корректный topic;
- корректный key;
- обязательные headers;
- схема payload;
- ожидаемый side effect.

### Negative

- invalid payload;
- отсутствующее обязательное поле;
- неизвестный enum;
- повреждённое сообщение;
- несовместимая schema version.

### Delivery

- duplicate event;
- retry;
- repeated delivery;
- consumer restart;
- временная недоступность downstream;
- потеря соединения;
- повторная отправка.

### Ordering

Если порядок важен:

- out-of-order;
- два события одной сущности;
- старое событие после нового;
- одинаковая версия;
- пропущенная версия.

### Idempotency

Проверить:

- повторный eventId;
- повторный business key;
- отсутствие повторного side effect;
- отсутствие лишней записи;
- отсутствие лишнего outgoing event.

### DLQ

Если используется:

- попадание в DLQ;
- содержимое сообщения;
- причина;
- повторная обработка;
- отсутствие частично выполненной операции.

## 5. Database

Если change влияет на данные, проверить:

### State

- состояние до операции;
- состояние после операции;
- связанные таблицы;
- количество записей;
- отсутствие дубликатов;
- обязательные поля;
- timestamps;
- created/updated metadata.

### Integrity

- PK/FK;
- unique constraints;
- consistency связанных сущностей;
- transactional consistency;
- отсутствие orphan records.

### History

Если используется история:

- создание history record;
- корректность старого значения;
- корректность нового значения;
- version;
- timestamp;
- actor/source.

### Delete

Если используется soft delete:

- признак удаления;
- исключение из обычных выборок;
- доступ через history/audit;
- повторное создание;
- ссылки связанных сущностей.

## 6. Интеграции

Для внешней системы проверить:

- успешный ответ;
- functional error;
- technical error;
- timeout;
- недоступность;
- медленный ответ;
- некорректный контракт;
- повторный вызов;
- retry;
- отсутствие двойного side effect;
- компенсацию/rollback, если применимо.

## 7. Логи

Проверить:

- наличие диагностически полезных сообщений;
- correlation/request/trace ID;
- правильный уровень логирования;
- отсутствие чувствительных данных;
- понятность ошибки;
- отсутствие необработанного stack trace там, где его быть не должно;
- наличие причины интеграционной ошибки;
- возможность проследить бизнес-сценарий через сервисы.

## 8. UI

Если change затрагивает UI:

- соответствие макету;
- состояния элементов;
- validation;
- error state;
- loading state;
- empty state;
- disabled state;
- адаптивность, если применимо;
- keyboard navigation;
- основные accessibility проверки;
- связь UI с фактическим backend state.

## 9. Повторяемость тестов

Тест должен быть:

- воспроизводимым;
- детерминированным;
- изолированным;
- независимым от порядка запуска;
- с понятными preconditions;
- с управляемыми тестовыми данными;
- с cleanup, если создаются долговременные данные.

## 10. Что запрещено считать достаточной проверкой

Недостаточно:

- только HTTP 200;
- только отсутствие exception;
- только наличие Kafka message;
- только наличие записи в БД;
- только успешное выполнение автотеста без проверки assertions;
- только happy path для критичного business flow.
